Customer sends a message
        ↓
Meta sends it to your server through a webhook
        ↓
Your bot checks the message and conversation history
        ↓
Find an answer from FAQs, business data, or AI
        ↓
Send the reply through Messenger’s Send API
        ↓
Save the conversation for future replies

A webhook is a public HTTPS endpoint that receives incoming messages from Meta.

FILES AND THEIR WORK

main.py
Creates the FastAPI app, defines webhook and health routes, and starts/stops resources.

techrock/config.py
Loads environment variables from the root .env file and defines the project root path.

techrock/db/database.py
Creates the MySQL database and missing tables; manages the SQLAlchemy engine and sessions.

techrock/db/models.py
Defines the jobs and history database tables using SQLAlchemy ORM models.

techrock/db/storage.py
Saves incoming messages, selects queued jobs, stores replies/history, and manages retry status.

techrock/services/chatbot.py
Uses LangChain and Groq to generate replies from knowledge.txt and conversation history.

techrock/services/messenger.py
Sends text replies to Messenger users through Meta's API.

techrock/services/worker.py
Processes queued messages, generates/sends replies, retries failures, and expires old messages.

techrock/__init__.py, techrock/db/__init__.py, techrock/services/__init__.py
Mark these folders as Python packages so their modules can be imported.

tests/test_webhook.py
Tests webhook verification, signatures, duplicate protection, ignored events, and reply processing.

tests/__init__.py
Marks the tests folder as a package for test discovery.

knowledge.txt
Stores verified information about The Tech Rock for the chatbot's answers.

.env
Stores actual API keys, Meta settings, and MySQL credentials; keep it private.

.env.example
Provides configuration variable names and example defaults without real secrets.

requirements.txt
Lists the Python dependencies needed to run the project.

.gitignore
Prevents secrets, virtual environments, caches, and local data from being tracked by Git.

README.md
Explains installation, configuration, running the app, testing, and current limitations.

workflow.txt
Describes the message workflow and each project's file responsibilities.

Suppose someone messages The Tech Rock: **“Do you know about earbuds?”**

1. **Customer → Meta**  
   Messenger sends the customer’s message to Meta’s servers.

2. **Meta → ngrok**  
   Meta forwards a message event to the public webhook URL you configured. ngrok passes it to your local server on port `8000`.

3. **ngrok → `POST /webhook`**  
   The route in `main.py` checks that the request came from Meta and belongs to The Tech Rock. It extracts the message and sender’s ID.

4. **→ MySQL jobs queue**  
   The message is saved in the `jobs` table with status `pending`. The webhook returns HTTP `200` to tell Meta it received the event.

5. **→ Worker**  
   The background worker picks up the pending message for processing.

6. **Knowledge + history → Groq**  
   The chatbot combines:
   
   - `knowledge.txt`: information about The Tech Rock.
   - Conversation history: recent messages from that customer.
   - The new question: “Do you know about earbuds?”

   LangChain builds the prompt, and Groq generates an answer.

7. **→ Messenger Send API**  
   `messenger.py` sends that answer and the customer’s sender ID to Meta, authenticated with your Page access token.

8. **→ Customer**  
   Meta displays the answer in the customer’s Messenger conversation. The worker marks the job `done` and saves the conversation history.

**ngrok handles incoming requests.** Your server sends outgoing replies directly to Meta’s API.

MANUAL MODE
- Page admin sends pause ai in the customer's Page inbox conversation.
- A signed message echo sets their MySQL conversation mode to manual and retires pending replies.
- Incoming messages remain stored, but the bot stays silent.
- Page admin sends resume ai; only new incoming messages get automatic replies.
- Customer requests to speak to a person also activate manual mode with no AI answer.
- Subscribe to both messages and message_echoes; the commands are visible to the customer.
- New tables: conversations (persistent mode), control_events (duplicate command protection).
- techrock/services/handoff.py detects common explicit human requests; chatbot.py handles other wording.

%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
The **`pause ai` command didn’t stop the bot** for two reasons:

1. **Page message echoes weren’t fully subscribed.** Customer messages reached the server, but your manual commands didn’t. Enabling `message_echoes` in both the app and Page subscriptions fixed delivery.
2. **The code rejected your Page inbox’s app ID.** Once commands arrived, the server still ignored them. We updated the filter to accept your inbox’s commands while ignoring the bot’s own replies.

After restarting the server, **`pause ai` and `resume ai` worked correctly**.

Earlier, replies also stopped because the server wasn’t running. Starting it restored service; trying to start a second instance caused the **port 8000 already in use** error.
IMAGES AND VOICE
- main.py queues image/audio attachments as well as text.
- job_media stores attachment URLs and cached transcripts/image observations in MySQL.
- techrock/services/media.py downloads Meta CDN media with size and redirect limits.
- Groq Whisper transcribes audio; Groq Qwen vision describes images.
- The existing chatbot uses this content and conversation history to send a text answer.
- Voice requests for a person activate manual mode; pause/resume still control media replies.
- Model defaults use the existing GROQ_API_KEY. No additional dependencies are required.
- Restart FastAPI after code changes; keep ngrok and webhook subscriptions running.
